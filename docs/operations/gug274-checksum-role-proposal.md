The entry identity and its shared scope, including the assigned group, are

The template excludes the two

A human's AWS CLI profile name is not an IAM principal ARN. Before binding an
entry role, separately verify its exact ARN/RoleId, assignment and ownership,
effective AssumeRole permission, MFA/session controls and shared permission-set
impact. If it is generated by Identity Center, changes belong in that
permission set's actual source of truth, not directly in AWSReservedSSO.
Recreated SSO roles can change identity: a previous review cannot silently
transfer to the new principal. [IAM role principals](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html),
[Identity Center permission sets](https://docs.aws.amazon.com/singlesignon/latest/userguide/permissionsetsconcept.html)

The Batch role's only trusted principal is the documented S3 Batch Operations
service, with `sts:AssumeRole`. No human or other service may directly assume
it through this trust policy. No undocumented SourceArn/SourceAccount condition
is invented. This service trust does not authenticate a historical report;
that remains a separate custody-verifier requirement.
[Batch role trust and permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/batch-ops-iam-role-policies.html)

## Permission boundary of the draft

| Role | Permitted by this draft | Deliberately outside the grant |
|---|---|---|
| Manifest writer | PutObject under the fixed custody bucket's `checksum/manifests/`; ListBucketVersions constrained to that prefix | GetObject/GetObjectVersion, report/audit writes, artifact access, deletes, job APIs, IAM and KMS changes |
| Batch writer | GetObjectVersion for one signed artifact key/version and one input manifest key/version; PutObject only under one reviewed report-run prefix; KMS Decrypt through regional S3 for the reviewed artifact key/context | Unversioned GetObject, RestoreObject, source writes, other report runs, ACL/tag mutations, deletes, job APIs, PassRole and resource-policy changes |

The manifest uploader can retain the PutObject response VersionId and use a
prefix-bounded version listing. These metadata permissions do not provide
content readback; any later verification read must use its separately reviewed
reader/verifier. Role permissions are maxima supplied by this draft, not
proof of successful provider access.

Batch GetObjectVersion grants are exact Resource and `s3:VersionId` bindings.
The six Batch bindings default to empty only in a fresh `ManifestOnly` stack,
where no Batch role is created. `BatchBound` rejects any empty binding; it never
creates a policy using an unconfigured value. The report
permission is limited to `checksum/reports/<reviewed-run>/`, including the
provider's nested output paths. Manifests and reports remain in the separate
SSE-S3 bucket; the artifact destination remains SSE-KMS.

The KMS grant is an identity-policy Decrypt statement, not a new KMS resource
grant. It is bound to one reviewed key ARN, `kms:ViaService` for
`s3.us-east-1.amazonaws.com`, and the artifact bucket ARN as encryption context.
S3 Bucket Keys use bucket-level context, so that condition does not impose an
object-key boundary. Exact S3 key/version permissions supply that separate
boundary. The object must be confirmed BucketKeyEnabled before this route is
used; do not widen the context automatically if the canary fails.
[S3 Bucket Key context](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-key.html),
[KMS ViaService](https://docs.aws.amazon.com/kms/latest/developerguide/conditions-kms.html#conditions-kms-via-service)

AWS's general Compute checksum permission example lists GetObject,
GetObjectVersion and RestoreObject. This draft deliberately targets exact
versions only. It has not demonstrated that the service's actual source and
manifest calls work with GetObjectVersion alone, or that Decrypt alone is
sufficient for this checksum operation. An authorized canary must test those
compatibility limits; an AccessDenied requires a new reviewed decision,
not adding broad permissions. Storage-class restoration is not authorized.
[GetObject permissions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)

The S3 permissions constrain objects and destinations, not the Batch operation.
GetObjectVersion plus PutObject can also permit copying an allowed source into
an allowed destination. The roles cannot enforce SHA256/FULL_OBJECT, distinguish
report content from other bytes, or limit the number of job submissions. The
future operator's request guard and producer verifier must enforce those
properties before this route can be accepted.

Effective access also depends on SCP/RCP, session controls, S3 policies, KMS
key policy and other grants. None were completely assessed here. An added
Allow cannot override a relevant Deny. The roles template itself does not
freeze future administrator changes or provide a permissions-boundary policy.
[IAM evaluation limits](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html)

## Operator permissions remain a separate review

The two task roles receive no job-operation or PassRole permissions. Verify
effective AssumeRole access for the exact manifest entry identity against
trust, boundary/session policies, SCP and explicit Denies. A direct trust grant
to a same-account principal may not need an additional identity-side Allow;
any needed permission delta requires separate review. Trust is not an Identity
Center assignment. [AssumeRole permissions](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)

The future job operator needs `s3:CreateJob` and `iam:PassRole` on the exact
same-account Batch role. The request context for a possible `iam:PassedToService`
restriction on CreateJob has not been confirmed here; do not assume a service
value or emit that grant yet. DescribeJob must later bind the actual returned
job ARN. No inline operator policy is attached or emitted as a deployable
grant in this iteration. [PassRole restrictions](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_passrole.html)

CreateJob cannot be represented as permission for one already-known job ARN:
the service has not allocated that job yet. Its permission requires Resource
`*`, and the documented conditions do not bind the checksum operation, source
versions, role and report settings together. Job tags or a scoped role are not
proof that a request uses SHA256/FULL_OBJECT, one task, the approved manifest,
the approved report settings or a finite job count. The future reviewed
operator/verifier must bound and validate the exact request, account/Region,
role, input bytes/version/ETag, source row, output namespace, operation,
confirmation and cost before an authorized send. An existing administrator
Allow remains broad even if a new narrow fragment is added.
[S3 job actions and conditions](https://docs.aws.amazon.com/service-authorization/latest/reference/list_s3.html)

Do not add CreateJob merely to make the role deployment useful. Prepare its
exact source-owned execution guard and prospective permission delta before
requesting job authorization. Existing NOT_CONFIGURED and capture-disabled
stops remain in effect.
